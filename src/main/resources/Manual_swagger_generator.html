📘 Manual Completo - Generador Swagger

🚀 1. Introducción

Este proyecto genera automáticamente documentación Swagger (OpenAPI) a partir de DTOs Java.

Permite:
  • ✔ Generar schemas dinámicamente
  • ✔ Construir ejemplos JSON automáticos
  • ✔ Personalizar valores mediante rules.xml
  • ✔ Resolver casos complejos mediante handlers
---

🏗️ 2. Arquitectura General

ComponenteResponsabilidad
SchemaBuilderConstruye JSON schema desde DTOs
ExampleGeneratorGenera ejemplos automáticos
RuleEngineAplica rules.xml
HandlersCorrigen casos complejos
ParserUtilResuelve nombres JSON
TypeUtilMapeo de tipos Java → JSON
---

🔄 3. Flujo de Ejecución

1. Leer DTOs (JavaParser) 2. Generar schemas (SchemaBuilder) 3. Generar example base 4. Aplicar rules.xml 5. Aplicar handlers especiales

⚙️ 4. Configuración

Importante: la configuración NO se hace por application.yml. El generador la carga en dos pasos, antes de que arranque Spring, a partir de la variable de entorno BM_HOME.
Paso 1 — archivo principal de la app
Ruta fija: ${BM_HOME}/appl/swagger-generator/config/swagger-generator.xml (un XML de java.util.Properties):
<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE properties SYSTEM "http://java.sun.com/dtd/properties.dtd"> <properties> <entry key="pathLog4jFile">${BM_HOME}/appl/swagger-generator/config/log4j2.xml</entry> <entry key="pathRules">${BM_HOME}/appl/swagger-generator/config/rules.xml</entry> <entry key="pathAbbreviations">${BM_HOME}/appl/swagger-generator/config/abbreviations.txt</entry> <entry key="pathServices">${BM_HOME}/appl/swagger-generator/config/services.xml</entry> <entry key="pathOutput">${BM_HOME}/appl/swagger-generator/output</entry> </properties>
Descripción:
  • pathLog4jFile → configuración de log4j2 a usar
  • pathRules → rules.xml externo (si no existe, se usa el bundled en resources/rules.xml)
  • pathAbbreviations → abbreviations.txt externo (idem, fallback al bundled)
  • pathServices → ruta al archivo de servicios (ver Paso 2)
  • pathOutput → carpeta donde se escriben los <servicio>.json generados
Si BM_HOME no está definido, o falta este archivo o alguna de las rutas que referencia, la aplicación registra el error en el log y termina (no continúa con valores por defecto).
Paso 2 — servicios a generar
Ruta indicada por pathServices arriba; cada <service> es un servicio que luego se genera vía GET /api/openapi/{name} (el name debe coincidir con el atributo name):
<services> <service name="creditos"> <controllersPath>C:\ruta\a\los\controllers</controllersPath> <beansPath>C:\ruta\a\los\dtos</beansPath> <beansPath>C:\otra\ruta\de\dtos</beansPath> <basePackage>com.mercantil.creditos</basePackage> <basePath>/creditos</basePath> </service> </services>
Descripción:
  • name → identificador del servicio, usado en la URL del endpoint del generador
  • controllersPath → carpeta con los controllers a escanear
  • beansPath → una o más carpetas con los DTOs a escanear (puede repetirse)
  • basePackage → solo se indexan como schema los DTOs de este paquete
  • basePath → prefijo de path que se antepone a cada endpoint generado

📚 5. abbreviations.txt

numero=num identificacion=id cuenta=cta nombre=nom fecha=fch monto=mto cliente=clte credito=cdto descripcion=descrip
Uso:
  • Normaliza nombres JSON
  • Evita nombres largos
  • Se aplica automáticamente

🧠 7. Responsabilidad por Clase

OpenApiGeneratorService
Orquestador principal del proceso
SchemaBuilder
Construye la definición JSON de cada clase
ExampleGenerator
Genera ejemplos con valores por defecto
RequestExampleProvider
Aplica los valores de rules.xml
RuleEngine
Parsea rules.xml
Handlers
Resuelven estructuras complejas
---

📜 8. Uso de rules.xml

<api path="/persona/consultar/ejemplo"> <request> <field name="codPaisEntrada" value="VEN"/> <field name="tipoIdEntrada" value="V"/> </request> <response> <field name="bodySalidaEjemplo.nomCliente" value="JUAN PEREZ"/> </response> </api>
❌ NO incluir headerEntrada ni headerSalida

📦 9. Reglas para Arrays y Objetos

---

⚠️ 10. Cuándo usar Handler

  • Flatten rompe estructura
  • Nested complejo
  • rules.xml no aplica
  • DTO con JsonCreator conflictivo
---

⚙️ 11. Ejemplo Handler

@Component public class EjemploHandler { public boolean supports(String path) { return path.equals("/endpoint"); } public void apply(Map example) { example.remove("bodyEntrada"); Map body = new LinkedHashMap(); body.put("campo","valor"); example.put("bodyEntrada", body); } }

🚨 13. Errores Comunes

rules no aplica → endpoint incorrecto
valores no cambian → usar handler
estructura incorrecta → flatten
---

🚀 14. Buenas Prácticas

  • ✔ Usar rules.xml primero
  • ✔ Handler solo si es necesario
  • ✔ No modificar SchemaBuilder innecesariamente
  • ✔ Probar endpoint individualmente
---

🏁 15. Conclusión

El sistema se basa en 3 capas:
  • DTO → estructura
  • rules.xml → valores
  • handler → lógica avanzada
